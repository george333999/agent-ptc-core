Why pricing uses DeepSeek only

DeepSeek's usage reliably returns prompt_cache_hit_tokens and prompt_cache_miss_tokens, which can be billed at the cache-hit price and the cache-miss price separately and map one-to-one to the official peak/off-peak prices. Other providers either do not return cache fields or define them differently, so like-for-like comparison is impossible; therefore cost and cache metrics use DeepSeek only. Amounts are estimates based on official unit prices; actual billing is subject to the provider.

Next optimization recommendations

  • Cache prefix stability: keep freezing the system and tool schema bytes so dynamic context is not inserted mid-task. This is currently the most certain gain.
  • Batch read-back: long conversations still involve multiple read_tool_result round trips. The next step is to read fragments for several result_ids in one pass, reducing model round trips rather than increasing compression further.
  • Tool result budget: adapt the budget to the context window and constrain the number of read-backs with a P90 duration limit; token reduction alone is not enough.
  • Suitable scenarios: multi-file read-only analysis that keeps the same context over time, cross-file refactoring, long reports and knowledge-base Q&A benefit most; one-off short Q&A, small single-file edits, hard real-time interaction and high-risk write operations that cannot be approved have limited benefit.
  • Accuracy regression: wire the artifact validation script into CI, run the 10, 20, 50, 70 and 100-turn regressions for every optimization change, and prefer rolling back rather than continuing to tune when accuracy drops.
